## Optimized Prompt

```
你是一位资深的技术项目经理兼架构师，精通 React + TypeScript + Zustand 技术栈和 AI API 集成开发。

## 背景

我正在开发一个名为「人格编年史」的暗黑奇幻 TRPG 网页游戏。当前已有一个可运行的单体版本（单次 AI 调用完成全部逻辑）。现在需要按照设计文档重构为 **4-Task 串并联架构**（叙事优先 → 三翼并行）。

## 输入文档（共 6 份，作为附件提供）

1. **决策流程设计.md** — 主架构文档，包含：决策流程图、节点到模块映射、4-Task 架构总览（§3.0-3.12）、调度时序、降级策略、Store 扩展、文件变更清单、实施路线
2. **task3-narrative.md** — Task 3 纯叙事生成（Phase A，streaming，最先执行）
3. **task1-reality-mapping.md** — Task 1 现实映射规则解析（Phase B-1，JSON 模式）
4. **task2-world-rules.md** — Task 2 世界法则触发判定（Phase B-2，JSON 模式）
5. **task4-choices.md** — Task 4 回合选项生成（Phase B-3，JSON 模式）
6. **task-ai-config.md** — Task 级 AI 配置设计，含现有系统分析（types.ts / aiEngine.ts / store / AiSettingsModal / constants.ts 五文件逐层剖析）、TaskAIConfig/TurnAIConfig 接口、DEFAULT_TASK_CONFIGS 预设、逐文件扩展方案、向后兼容迁移路径

## 现有代码基线

- `types.ts`：Phase、Character、RuleCard、StatKey、StoryChoice、EngineResult、GameState、DecisionRecord、ServiceProvider、OpenAIConfig、AIConfig
- `services/aiEngine.ts`：AIProviderConfig、CompletionRequest、generateContent()、generateStream() — 均无 temperature/maxTokens/超时/重试
- `services/geminiService.ts`：当前单体 processTurn()（将保留为 fallback）
- `store/index.ts`：Zustand + persist，扁平 AI 配置（provider/geminiKey/openaiConfig）
- `constants.ts`：CHARACTERS、INITIAL_RULES、INTRO_STORY，无 AI 配置常量
- `components/AiSettingsModal.tsx`：扁平 Provider 配置 UI
- `components/RealityMappingPanel.tsx`、`RuleCard.tsx`：待接入 AI 分析结果
- `App.tsx`：handleChoice() 当前直接调用 geminiService
- `utils/ruleParser.ts`、`ruleValidator.ts`：客户端降级逻辑

## 任务

请基于以上 6 份设计文档和现有代码基线，输出一份 **完整的、可直接执行的任务规划说明文档**，要求如下：

### 输出结构（严格遵循）

#### 一、项目总览
- 一段话概括项目目标和架构变更（从单体到 4-Task 串并联）
- 涉及文件清单（新增 / 修改 / 保留），引用 §3.10 文件变更清单

#### 二、分阶段任务分解
按 4 个实施阶段（Phase 1-4），每个阶段下拆分为 **可独立验收的原子任务**，每个任务包含：

| 字段 | 要求 |
|------|------|
| 任务 ID | 格式 P{阶段}-T{序号}，如 P1-T01 |
| 任务标题 | 清晰简洁 |
| 涉及文件 | 精确到文件路径 |
| 前置依赖 | 列出依赖的任务 ID（无则写"无"） |
| 输入 | 该任务开始前需要什么（接口定义 / 上游输出 / 设计文档章节） |
| 输出 / 交付物 | 完成后产出什么（代码文件 / 接口 / 测试用例） |
| 详细步骤 | 3-8 条具体操作步骤，包含关键代码变更描述（不需要完整代码，但需指明修改位置和修改内容） |
| 验收标准 | 2-4 条明确可测试的 Done 条件 |
| 预估工时 | 小时为单位 |
| 风险与注意事项 | 可能踩的坑、向后兼容注意点 |

#### 三、依赖关系图
用 Mermaid gantt 或 flowchart 画出所有任务的依赖关系和并行可能性。

#### 四、关键技术决策检查清单
列出实施过程中需要确认的技术决策点（如：Gemini streaming + JSON 解析策略、localStorage 迁移版本号、降级触发条件阈值等）。

#### 五、测试策略
- 单元测试：每个 Task 的 JSON 解析 / 降级逻辑
- 集成测试：turnOrchestrator 串并联调度
- E2E 冒烟测试：完整回合流程

#### 六、里程碑与交付节奏
按周为单位的交付计划，标注每个里程碑的 Demo 验收点。

### 约束

- 语言：简体中文
- 所有任务必须引用对应的设计文档章节号（如"参见 task3-narrative.md §4"）
- 保持与 6 份设计文档的完全一致性，不可引入文档中未定义的接口或行为
- 严格遵循 task-ai-config.md 中的逐文件扩展方案和实施顺序（Step 1-6）
- 向后兼容是底线：每个任务完成后现有功能不可回归
```

## Optional Enhancers

可根据需要追加到 prompt 末尾：

| 增强项 | 追加内容 |
|--------|---------|
| **代码片段** | `每个任务的"详细步骤"中，对关键修改点提供 TypeScript 代码 diff 片段（修改前 → 修改后），不超过 20 行` |
| **风险矩阵** | `新增"第七节：风险矩阵"，按 影响(高/中/低) × 概率(高/中/低) 列出 Top 10 风险及缓解措施` |
| **Prompt 工程任务** | `为每个 AI Task 新增一个专属的 Prompt 调试子任务，包含：baseline prompt 编写、A/B 测试方案、输出质量评分标准` |
| **CI/CD 集成** | `新增"第八节：CI/CD 流水线变更"，描述每个 Phase 完成后需要更新的自动化测试和部署脚本` |
| **多人协作** | `为每个任务标注建议的负责人角色（前端/AI工程/全栈），并标注可并行分配给不同开发者的任务组` |
